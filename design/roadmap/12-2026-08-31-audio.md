## The search and the gate were the same number three times, and never the same ruler (2026-08-31, tools + assets)

*"音效已经加了，现在来讨论背景音乐."* The SFX set had been complete for a day; music had never existed
as anything but a settings slider wired to `setMusicVolume(_v) => {}`. This pass produced the first
two shipped loops and the pipeline that cuts them. **It produced no runtime**: nothing in the client
reads either file, which is stated here because the status boxes are the place that drift.

### The division of labour, decided before any work

I have no audio channel at all — this is stronger than the looking-is-not-evidence problem in
rendering, where a real frame can at least be extracted and sampled. So the pass was split at the
line where measurement stops: **I own the region choice, the level, the loop seam, the byte budget
and the gate; the user owns whether it sounds right.** Both AI masters were generated by the user
from briefs written here, and the two verdicts below are measurements, not opinions.

### What the measurements said about two AI masters

`audit.py`'s existing `spectral()` reads only the first 32768 samples — the entire file for a 100 ms
cue, and **0.68 s of a 4-minute track**. It reported a 343 Hz centroid and a 175964 ms attack for the
first master, both meaningless. A whole-track band analysis was the first thing built, and it found:

- **`Frozen Resonance`** was prompted as a calm crystal-bell menu bed and came back as a **sub-bass
  drone**: 90% of its energy below 109 Hz, 95% below 198 Hz, nothing above 2 kHz, and its 40-49 Hz
  band 13 dB above every other band. Reassigned to `boss`, where dread is the brief.
- **`Crystal Menu`**, generated after `sub-bass`/`drone` went into the exclude list, moved up two
  octaves (40-49 Hz from -21.2 to -66.0 dBFS) and became the menu bed. It still produced **nothing
  above 4 kHz**, so "high register sparkle" has now failed twice in the same direction — that is the
  service's tendency, not a coin flip.
- **Both masters peak at -0.1 dBFS.** The shipped cue set peaks at **-14 to -21**, because it was
  deliberately peak-matched down to the synth voices it replaced. Every AI master needs ~15 dB off
  before it belongs in this mix; that is one number, `MID_TARGET_DBFS = -30`, and the `music` gate
  now enforces it.

One claim from the previous pass had to be corrected: *"deflect and impact live above 2 kHz"* is half
wrong. Measured per band, `deflect` peaks in 2-8 kHz (-32.1) but `impact` (-33.7) and `muzzle` (-22.9)
both peak in **250-2000 Hz**. The band music has to stay out of the way of is 250 Hz-8 kHz, weighted
toward the bottom of that — which is what the level target is measured in.

### The mistake, three times

The region search and the acceptance gate have to be **literally the same measurement**. They were
not, three times running, and each time the search returned a candidate that then failed:

| search said | gate measured | why |
|---|---|---|
| 3.01 dB | 5.61 dB | the search scored a 2 s crossfade window from four 4096-point frames — 16 k of its 96 k samples. Sampling a window is not measuring it. |
| 2.44 dB | 3.39 dB | the gate weighted per-band differences by energy; the search averaged all 30 bands equally. |
| 1.41 dB | 3.69 dB | the search read the *raw* master, but `boss` always gets a low shelf, and attenuating its dominant sub moves the energy weighting onto the mids, where its ends differ more. |

The fix each time was to delete the second implementation, not to retune it: both sides now call
`audit.profile_diff(band_profile(...), band_profile(...))`, and `--search` applies the track's shelf.
Search, extraction and post-encode figures now agree to within 0.02 dB (`menu` 1.15 / 1.15 / 1.15;
`boss` 1.62 / 1.64 / 1.63). The general shape is worth keeping: **a ranking metric that is not the
acceptance metric is a generator of near-misses.**

### The gate that had to be built rather than reused

`audit.py` already had a `loop` class, and it was the wrong gate for this player. It requires
`step_db <= -50` — the last sample sitting next to the first, which is what `el.loop = true` needs —
and MP3 frame padding makes that unavailable regardless. Since track-to-track changes need a
crossfade anyway, the player reuses it to close the loop (a second deck starts at `length - 2 s`), so
the real requirement is that the two ends are **tonally compatible over 2 s**, not continuous.
The new `music` class drops `step_db`, allows stereo (a 69 s bed streams; a 100 ms cue's second
channel is pure overhead), and adds `xfade_band_diff <= 2.5` plus `mid_band_dbfs` in `[-31, -29]`.

Routing had to change too: files reach the `music` class **by directory**, because a track named
`menu.mp3` matches no cue prefix, fell through to the caller's default, and both beds were reported
as "too long" and "stereo wastes bytes" — the same shape as the `pickup.*` mis-routing this gate
already had a regression test for.

### Four bugs the checks caught, and one they did not

Every measurement here was checked against synthetic signals with known answers, and four of the
five things that were wrong were found that way, not by reading:

- **An FFT normalisation that calibrated peak amplitude while reporting RMS** (a 100 Hz sine read
  -4.44 dB where -6.02 was expected; the honest expectation was -9.03, and the assertion was as wrong
  as the code).
- **A block loop that never executed on short input.** `band_rms` used a fixed 65536-sample block, so
  every 0.1 s cue read `-inf` in every band — which looks exactly like "this cue has no energy" rather
  than "nothing was measured".
- **An empty band returning `-inf`**, so differencing two profiles gave `nan`. Real inputs hit this:
  after resampling, every band above the new Nyquist is exactly zero. `nan` also fails `< limit` *and*
  fails `> limit`, so the assertion phrasing mattered — `assert x < 0.5` caught it where
  `assert not (x > 0.5)` would have passed.
- **A 2nd-order low shelf that under-delivered where it was aimed**: -6.9 dB at 40 Hz for a -14 dB
  shelf at 80 Hz, when 40-49 Hz was the exact band it existed to tame. Now 4th-order, and the
  selfcheck asserts the *requirement* (near-full cut by f0/2, unity by 4·f0, monotonic between)
  rather than restating the algebra.
- **The one the checks did not catch**, because it was mine and outside the tool: `pathlib.write_text()`
  uses the Windows locale encoding, so a doc patch wrote cp1252 em-dashes into a UTF-8 file *and*
  silently failed every replacement pattern containing one — 4 of 5 edits no-oped and the file was
  left invalid UTF-8. Explicit `encoding="utf-8"` on both ends, plus a decode check after writing.

An honest note on `xfade_band_diff`'s weighting, since it is the number everything else keys off:
unweighted, it averaged 30 bands equally, so bands near -100 dBFS — where the only content is FFT
leakage whose phase differs between the two windows — dominated the result. A two-sine bed whose
head and tail were **identical by construction** measured 6.12 dB that way, enough to fail a 3.5 dB
gate on nothing at all. Weighted by the louder of each band's two windows, the same fixture reads
0.01 dB.

### What shipped

- `tools/audio-pipeline/process_music.py`, new (405 lines): shelf-aware region search, 4th-order
  zero-phase low shelf, band-target level normalisation, stereo spectral resample, and an encoder
  search that keeps the smallest MP3 over (rate × VBR quality) **whose decoded band levels stay
  within 1.5 dB of the pre-encode signal** — measured, not assumed, so a setting that quietly dulls
  the bed cannot win on bytes.
- `audit.py`: the band-measurement layer (`band_profile`, `band_rms`, `profile_diff`,
  `xfade_band_diff`, `music_measures`), the `music` gate class, and directory-based routing.
  `process_music.py` imports the measurement rather than owning a copy.
- `selftest.py`: **15 → 23 cases.** All eight new ones pin a bug that actually happened above.
- Two shipped loops, **1.09 MB**, both passing `--class music`; the 52-file `--by-cue` sweep over
  `public/audio/` still passes, and `client/src/platform/audioAssets.test.ts` + `src/audio` are green
  (101 tests) — the latter unaffected because it reads the directory non-recursively, which is also
  why music has no TS-side byte gate yet.

### The byte gate went off, and what it found underneath

Dropping 1.09 MB into `client/public/audio/music/` failed `npm run check` immediately: with no
rule in `assetPacks.json` the files fall to `defaultPack: "main"`, and the WeChat main package
went from 4.00 to **5.09 MB against a hard 4.00 MB limit**. design/11 had already predicted the
fix ("a future music subpackage is a prefix rule in `assetPacks.json`, not a loader change") and
that is exactly what it took: one pack entry, one `/audio/music/` prefix rule, no loader and no
manifest change. `SUBPACKS` is derived from that file, so `ensureAllPacks()` will call
`wx.loadSubpackage` for it at boot with no further wiring.

That pack is justified differently from the four before it, and the `$comment` block now says so.
The biome and boss packs are deferred because their contents are **unreachable** in a fresh run;
`menu` is wanted on the very first screen. Music is deferred purely on **bytes** — it is the one
asset class a game can start without.

**What the gate found underneath is worse than what it was reporting.** With music moved out,
main measures **4,191,575 of 4,194,304 bytes — 2,729 bytes of headroom**, 99.93% full. Nothing
in this pass caused it (music is in its own pack; main's assets are 3.24 MB and the code bundle
0.95 MB), and the last recorded figure was 3.42 MB on 2026-08-30, so ~770 kB arrived from other
work since. Two things follow. First, **the next code change of any size fails this gate**, which
matters immediately because the music *runtime* is the next pass and it lands in `js/game.js`.
Second, the gate measures **uncompressed**: the checker's own note says main is ~3.36 MB gzipped,
so if WeChat bills the compressed package there is real slack and the emergency is with our
measure rather than with the platform. Which of those two it is has never been checked on a
device — the same open item as every other WeChat audio question here.
